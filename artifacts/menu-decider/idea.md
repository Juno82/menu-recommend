# Menu Decider

## Problem Statement
HMW — 매끼니 메뉴 결정 피로를 겪는 사람에게, 현재 맥락(날씨·시간대·당사자 조건)을 합성해 '검색 결과 여러 개'가 아니라 *'오늘 이 메뉴' 하나의 답*을 주고, 그 답을 행동으로 옮길 수 있도록 *근처 식당까지 한 화면에서* 연결해줄 수 있을까?

## Recommended Direction

**결정 1개 머신 + 식당 부착 하이브리드.** 화면은 두 영역으로 나뉜다.

1. **메인(상단)**: 메뉴 카드 1장. 메뉴명 + 한 줄 추천 이유. *"비 오는 화요일 오후 1시, 느끼한 거 빼달라는 당신 → 칼국수."*
2. **부착(하단)**: 그 메뉴를 파는 *것으로 추정되는* 근처 식당 Top3 + 지도. 카카오 로컬 API로 검색·표시.

**왜 하이브리드인가.** 순수 B(메뉴만)는 "그래서 어디 가지?"가 남아 결정 피로 해결이 절반에서 끝난다. 순수 A(원안)는 메인이 검색 결과 UI로 회귀해 *결정 1개* 가치 가정을 검증하기 어렵다. 하이브리드는 **메인에서 가치 가정을 검증하면서, 하단으로 행동 마찰까지 줄인다**.

**메뉴 사진/가격은 LLM 추정 생성으로.** 카카오 로컬 API는 식당 단위(이름·위치·카테고리)만 주고 메뉴 단위 데이터를 주지 않는다. MVP에서는 LLM에게 *"이 식당의 카테고리상 추정 대표 메뉴와 일반적 가격대"*를 생성하게 한다. **이건 hallucination 위험을 의식적으로 수용한 결정이다** — UI에 "실제 메뉴는 가게에서 확인" disclaimer를 명시하고, 진짜 답을 주는 곳은 메뉴 카드 1장이라는 점을 유지한다.

**차별성 평가는 정직하게.** UI 자체는 카카오맵 대비 우위가 없다. 차별점은 *'한 줄 입력 + 자동 맥락 변수(날씨·시간대) 합성'*이 카카오맵 기본 검색보다 *진짜로 더 좋은 답을 주는지*에 달려 있다. 이게 핵심 가정 1.

## Key Assumptions to Validate

**Must Be True**
- [ ] **맥락 합성이 '한 줄 프롬프트만 보낼 때'와 다른 답을 만든다** — 동일 프롬프트로 '날씨/시간 포함' vs '미포함' 10회 비교. 답이 거의 같으면 제품 자체가 가치 없다
- [ ] **사용자가 매끼 결정 피로를 실제로 겪는다** — 본인을 1주일간 사용자로 두고 매끼 도구를 켜는지 관찰

**Should Be True**
- [ ] **LLM이 추정한 식당별 메뉴/가격이 사용자가 보기에 그럴듯하다** — 30개 식당 샘플로 자문: "이 정도면 신뢰할 만한가, 아니면 너무 가짜처럼 보이는가". 후자면 메뉴 추정 자체를 제거하고 식당 정보만 노출
- [ ] LLM 응답 1–3초가 인내선 안 — 실측. 초과 시 스트리밍/캐시
- [ ] '메뉴 카드 1장(메인) + Top3(부착)' 레이아웃이 '카드 1장만' 또는 'Top3만' 보다 만족도 높다 — 본인 1주일 자문

**Might Be True** (지금은 검증하지 않음)
- 실제 메뉴 사진(스크래핑/별도 소스)이 있어야 결정에 도움이 된다
- 이전 선택 이력이 가치를 더한다

## MVP Scope

**포함**
- 단일 페이지. 자유 프롬프트 입력 1줄 ("느끼한 거 빼고", "혼밥", "해장")
- 위치: 브라우저 Geolocation (거부 시 수동 지역 입력 fallback)
- 위치 기반 날씨 자동 조회 (Open-Meteo, 무료·키 없음)
- 시간대 자동 판정 (아침/점심/저녁/야식)
- LLM 호출 → 메뉴 1개 + 한 줄 이유
- **상단: 메뉴 카드 1장** (메뉴명 + 이유)
- **하단: 근처 식당 Top3** — 카카오 로컬 API 키워드 검색(`{메뉴명}` 또는 카테고리)
  - 각 식당: 이름·도보 거리·카카오맵 상세 링크
  - LLM 추정 대표 메뉴 1-3개 + 추정 가격대 (disclaimer 필수)
  - 카카오맵 JS SDK 지도에 핀 3개
- "다시 추천" 버튼

**제외**
- 로그인·이력 — Must Be True 검증 전에는 무가치
- 모바일 앱 — 웹 1페이지로 충분
- 영양/알레르기 필터 — '결정 피로'와 다른 문제
- 실제 메뉴 사진 — 신뢰할 만한 소스 없음. 시각 유혹은 painkiller가 아닌 vitamin

## Not Doing (and Why)
- **실제 메뉴 데이터 소스 통합** — 카카오맵 스크래핑 / 망고플레이트 / 배민 API는 TOS·신청·복잡도 모두 개인 프로젝트 범위 초과. LLM 추정으로 시작하고 그게 부족하면 그때 결정
- **메뉴 사진 자동 수집** — Google Images 등은 라이선스·품질 위험. MVP는 텍스트 only
- **이전 선택 이력 / 로그인** — 가장 강한 맥락 변수이지만 인프라 비용 발생. Must Be True 가정 검증 후 추가
- **알레르기/칼로리 필터** — 다른 문제 도메인. 프롬프트에 자유 입력으로 우회

## Open Questions
- **LLM 제공자**: Anthropic Claude 4.7 vs OpenAI vs 양쪽 모두 지원? 비용/지연으로 결정
- **LLM 호출 횟수**: 메뉴 1번 + 식당별 메뉴 추정 1번씩(3번) = 총 4번? 아니면 1번 호출에 다 포함? 응답 시간/토큰 비용 트레이드오프
- **카카오 키 관리**: 카카오 로컬 REST API 키 + 카카오맵 JS SDK 키. 환경변수, 도메인 화이트리스트
- **Geolocation fallback UX**: 사용자가 위치 권한 거부 시 — 수동 입력? 기본 지역(서울 강남역) 가정? 둘 다?
- **메뉴 후보 풀**: LLM 자유 생성 vs 사전 정의 500개 풀에서 선택 (후자가 평가·디버깅 쉬움)
- **같은 입력 반복 시 *다른* 결과를 줘야 하는가** — 일관성 vs "다시 추천" 의미
- **Hallucination disclaimer 표시 방식** — 식당 카드의 추정 메뉴/가격에 어떻게 명시할 것인가 (작은 회색 텍스트? 툴팁? 별도 섹션?)
